Transaction and limitations
---------------------------
The existing credit RPC keeps its signature, arithmetic and duplicate path.
Its only functional addition inserts a receipt after the paid-purchase update,
inside the SAME credit transaction. Credit + receipt commit before the API
attempts delivery. If receipt persistence fails, uncommitted credit rolls back;
this is distinct from a Telegram failure after commit, which cannot undo credit.
The API adds only an import, post-credit hook and notification result field.

Purchase ID and Checkout session each have a unique outbox constraint. Claim
rechecks paid purchase, session, recipient, minutes/seconds, package, amount,
currency, paid timestamp and balance evidence, with no new subscription gate.
This preserves Owner/Admin behavior and purchased minutes after plan expiry.
Unpaid/failed/cancelled/expired paths do not dispatch. Duplicate paid purchases
do not create missing receipts: no retrospective sending or backfill.

Telegram has no sendMessage idempotency key. Exactly-once delivery cannot be
guaranteed across a lost response/process crash. Ambiguous timeout, malformed
response, 5xx, wrong returned chat or lost DB acknowledgement are NOT resent.
Persisted sending intent becomes uncertain on a subsequent claim after lease
expiry; if no subsequent dispatch occurs it remains sending, not retryable.
Manual review is required; never reset uncertain/sending to pending blindly.
Only an explicit 429 rejection is retry-eligible, subject to existing due time
and five-attempt cap. Definitive 4xx rejection is terminal.

No scheduler is introduced. Delivery is attempted immediately after a successful
credit RPC. A safely pending/due-retry receipt can be dispatched through the
existing authenticated admin /admin/dispatch endpoint in payment-aftercare;
duplicate new Stripe processing may also revisit an existing receipt. Existing
webhook event deduplication is unchanged and must NOT be relied on as a worker.
Missed dispatch/crash-before-hook remains durable for operator dispatch. No
automatic sweep/backfill is included. Admin overview remains plan-only to avoid
changing existing UI contract; addon receipt IDs are available to an authorized
operator from payment_notification_outbox. The existing admin dispatch endpoint
can handle both event types after this candidate is deployed.
